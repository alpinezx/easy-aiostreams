# AIOManager (advanced)

> New to this? Start with the [basic guide](../basic/aiomanager.md).

## What it runs

`setup-aiomanager.sh` adds one container next to AIOStreams, the same way AIOMetadata and MediaFlow Proxy do:

- **`aiomanager`**: [AIOManager](https://github.com/sonicx161/aiomanager)'s image (`ghcr.io/sonicx161/aiomanager`), pinned to an exact release such as `2.0.0`, never `latest`. Updates change the pin (see [Updates](#updates-and-going-back)). AIOManager's "build" releases (`v1.8.5+build.2`) have no image of their own, so the script only offers plain versions.

It sits on the shared `aios_shared` Docker network with no published ports. Caddy serves the subdomain (`caddy.d/56-aiomanager.caddy`) and reverse-proxies to `aiomanager:1610`, with the HTTPS certificate handled like your main site's. It uses SQLite, so there's no database container; on a test server it used about 135 to 185 MB of memory.

Everything it keeps is in `/opt/aiostreams/aiomanager-state/`:

| | |
|---|---|
| `config` | subdomain, the pinned release, and whether sign-ups are open (and until when) |
| `aiomanager.env` | the settings AIOManager reads (mode 600) |
| `docker-compose.yml` | its container, with a health check on `/api/health` |
| `data/` | its database (`aio.db`, with `aio.db-wal` and `aio.db-shm` beside it) and `server_secret.key` |

`server_secret.key` is generated by AIOManager on its first start. It decrypts what AIOManager keeps encrypted on the server (autopilot rules, Stremio auth keys, connection credentials), so it's treated like a password: the script never prints it, the control panel never reads it, and it only leaves the server inside a backup.

The settings the script gives AIOManager:

- **`TRUST_PROXY=true`**, so AIOManager's rate limits see each visitor's real address. Safe here because Caddy replaces any `X-Forwarded-For` a visitor sends rather than adding to it.
- **`CORS_ORIGINS=https://<your subdomain>`**, so its API only answers pages from its own address.
- **`REGISTRATIONS_CLOSED`**, which is how sign-ups are opened and closed (below).

## Logins and sign-ups

AIOManager has no admin user. Each **login** is a UUID and password: AIOManager makes the UUID, and you pick the password. There's no reset, and nobody can see or manage anyone else's login, the server owner included. Its data (accounts, addons, autopilot rules) is encrypted in the browser before it's synced to the server.

Anyone who can open the address can make a login while **sign-ups** are open, so the script keeps them closed except while you need them:

- **First setup** opens them, waits while you make your login, checks one exists, then closes them. Typing `later` there leaves them open for an hour instead.
- **Option 10** (or the control panel's switch on the Add-ons page) opens them for **30 minutes**, or closes them now.
- **They close by themselves.** Opening them writes a systemd timer (`aiomanager-signups-close.timer`) for the closing time. It's `Persistent`, so if the server is off at that moment it runs soon after it's back. Closing removes the timer again.
- **A restore, or Start from the control panel, closes them.** A backup made while they were open doesn't reopen them.

Opening or closing them restarts AIOManager with the new setting, which takes a few seconds. To do it from a script, or over SSH without the menu:

```bash
sudo bash /opt/aiostreams/setup-aiomanager.sh signups open [minutes]
sudo bash /opt/aiostreams/setup-aiomanager.sh signups close
sudo bash /opt/aiostreams/setup-aiomanager.sh signups status
```

**Status** and the control panel show how many logins there are. The script asks AIOManager's own database for it, read-only, counting rows with a password (the rest are AIOManager's own bookkeeping).

## Updates and going back

Releases are pinned, so nothing changes until you update. Three ways, all the same underneath:

- The control panel: **Update** on AIOManager's card, with **Back up first** ticked.
- The menu: **7) Update**, which also lets you pick an older version.
- A command, which asks nothing:

```bash
sudo bash /opt/aiostreams/setup-aiomanager.sh update-aiomanager [--backup] [--version X.Y.Z]
```

It pulls the release, restarts AIOManager and waits up to 90 seconds for it to report healthy. If it doesn't, it shows the last log lines, puts the previous release back and removes the one that failed. A version that doesn't exist is refused before anything changes.

Going back to an older release warns you first, in case a newer one changed the database. When this was tested, 1.8.5 and 1.5.4 both read 2.0.0's data without trouble, and moving back up to 2.0.0 afterwards was fine too, but keep the backup anyway.

Restoring a backup made with **Back up first** brings back the release from before that update, as the backup is taken before switching.

The control panel checks GitHub for new releases at most every 3 hours, only while you have it open, like AIOStreams' own.

## Backups

A backup holds `aiomanager-state/`: its settings, its database with every login and everything synced to it, `server_secret.key`, and a note of whether it was running. SQLite keeps recent changes in `aio.db-wal` until it folds them into `aio.db`, so the three files have to be copied together: AIOStreams and AIOManager are paused together for a few seconds while the backup is written, so they're copied at rest. Debug traces (`trace.log*`, only written when AIOManager's tracing is switched on) are left out.

A restore checks AIOManager's subdomain points at the server, then starts it again if it was running, with sign-ups closed. Restoring over SSH on a new server or domain offers to move it to a new subdomain: its address, its Caddy site, its certificate and its `CORS_ORIGINS` all follow. Sign in at the new address with your UUID and password; if your accounts don't appear, use **Pull from Cloud** in its Settings. The control panel's **Restore** is for rolling the same server back only, and refuses a backup whose AIOManager subdomain differs from this server's.

Backups from before AIOManager was added (format 5 or older) can't say whether it was running, so a restore leaves it off and prints the command to start it.

More on backups in general: [Backup & Restore (advanced)](./backup-restore.md).

## Phone alerts

With the [watchdog](./watchdog.md) set up, AIOManager joins its checks by itself once installed:

- **Every 2 minutes:** Caddy is running, AIOManager's container is running, and it answers `/api/health` (asked through Caddy), which also fails if its database isn't healthy. Two failures in a row send the usual down alert, saying what failed; the all-clear follows when it passes again. **3) Stop** leaves a marker, so stopping it on purpose doesn't alert.
- **New releases (optional):** off until you switch it on, on the control panel's Phone alerts page or as option 9 in the watchdog's Extra alerts menu. One alert per release, checked every 6 hours.

## Control panel

Once AIOManager is installed, the [control panel](./control-panel.md) shows:

- **Its own Overview card**: the release it runs, the newest one, **Update**, **Check now**, **All releases**, and a **Dashboard** link beside its title. Its corner shows how many logins there are, or, amber, **Sign-ups open** while they are. It folds and can be hidden or moved with **Edit**, like the other cards.
- **A card on the Add-ons page**: its address, the **sign-ups switch** (on opens them for 30 minutes, off closes them now), the number of logins, its version and certificate, and **Uninstall**.
- **A row in Services** with **Logs**, **Restart** and **Stop** / **Start**, and its branch off Caddy in the request flow.
- **A row on the Scripts tab**, as an optional add-on.

The panel reads only the subdomain, the pinned release and the sign-ups setting from `config`. It never reads `server_secret.key`.

## Menu reference

```bash
sudo bash /opt/aiostreams/setup-aiomanager.sh
```

1. **Status**: running or not, address, release, sign-ups, logins, and whether a newer release is out
2. **Start**: brings it up (installs it, the first time, and opens sign-ups for your first login)
3. **Stop**: stops the container, keeping everything, and leaves the "stopped on purpose" marker
4. **Reconfigure**: change the subdomain
5. **Test**: checks it answers inside the server and over HTTPS, and that sign-ups are as set
6. **Show address**
7. **Update**: the newest release, or an older one, with a backup first if you like
8. **Uninstall**: type `uninstall` to confirm. Removes the container, the Caddy site, the sign-ups timer and `aiomanager-state/` (every login with it), and optionally the downloaded image. Only the script itself stays.
9. **Show recent logs**
10. **Sign-ups**: open them for 30 minutes, or close them now
11. **Exit**

The commands the control panel uses ask nothing: `start-aiomanager`, `stop-aiomanager`, `update-aiomanager`, `signups open|close` and `uninstall [remove-image]`.
